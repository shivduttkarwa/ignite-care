01The whole thing in one paragraph

Ignite runs three residential care homes. In each home, every participant has a paper book, and every shift a support worker writes what happened — what they ate, whether they showered, how they slept. The next worker reads the book before starting.

This portal replaces the book. A worker opens it on their phone, sees the participants they still need to write up this shift, fills in a form, and submits. The moment they submit, the system freezes that record, turns it into a PDF that looks exactly like the paper form, and files it. A participant's whole book is those PDFs stapled together, oldest first — one file, downloadable any time.

Everything else exists to serve that loop: who can see whom, what the manager sees, how the client pulls a month of bowel data into a spreadsheet, and how it stays trustworthy enough for an NDIS audit.

02Two programs, one website

This is the single most important thing to understand about the shape of the codebase, and it is the change from the first version.

Most web apps are one program. The server reads the database, builds a finished HTML page, and sends it. The browser just displays it. Simple, and it works — that is how WordPress works, and how this portal was originally built.

This portal is now two programs that do not know anything about each other's insides:

The back endPython · Django

Owns the database, every rule, and the PDF machinery. It sends data, never pages. Ask it for a participant and it replies {"id": 4, "full_name": "Daniel Reeves", "room": "Room 2"}. It has no idea what a screen looks like.

The front endTypeScript · React

Owns every pixel. It runs inside the browser, asks the back end for data, and draws the screens from it. It has no idea what a database is.

Between them sits an API — an agreed list of addresses you can ask for data, and the exact shape of the answer. Here every one of them starts with /api/.

Why bother, when one program worked?

Three reasons, in the order they actually matter to this client.

A phone app is comingThe real reason

A native app cannot use HTML pages. It needs data. If the only way to get data out of the system is to build an API later, that is a rewrite of the entire back end at the worst possible moment. Now the API is the back end — an app is a third client alongside the browser, not a second system.

The two halves can change independentlyDay to day

Redesigning a screen touches no Python. Adding a database column touches no React. Two people can work on the same feature without stepping on each other, and a front-end change cannot break a business rule because it is not allowed anywhere near one.

The rules live in exactly one placeSafety

Every client — this website, a future app, a future integration — has to come through the same API and obey the same checks. There is no second copy of "a worker may only see their own house" to drift out of step.

The honest cost Decoupling is genuinely more work than one program: two languages, a build step, and data that must be described twice — once in Python, once in TypeScript. It is worth it here because a mobile app is a stated intention rather than a hypothetical. If it were not, one program would have been the better engineering call.

03Every technology, in plain words

Here is every piece, what it is, and what it is for in this project.

The back end

PythonLanguage

The language everything server-side is written in. Chosen because the best PDF tool in existence is a Python library, and because it reads almost like English, which matters when someone else has to maintain this in five years.

DjangoFramework

A framework is a pre-built skeleton for a web app — it already knows how to handle logins, talk to a database, and turn a web address into code, so you only write the parts unique to your project. Django is the most established Python one. We use the LTS release (Long Term Support): security patches guaranteed until 2028, which matters for a system holding clinical records.

Django REST FrameworkAdd-on · "DRF"

The layer that turns Django from a page-builder into a data service. It handles converting database rows to JSON and back, paging long lists, refusing unauthenticated callers, and returning proper error codes. It is the reason the API was days of work rather than weeks.

PostgreSQLDatabase

The filing cabinet. Every participant, worker, record and audit entry is a row in a table. We use SQLite on your laptop (a database that is just a single file — zero setup) and PostgreSQL on the real server. Django talks to both identically, so no code changes.

JSONA way of writing data

Not a technology so much as a notation — curly brackets, names and values. It is what the two halves speak to each other. {"full_name": "Daniel Reeves", "room": "Room 2"} is JSON. Every language on earth can read it, which is why an app, a website and a spreadsheet script can all talk to the same API.

The front end

ReactLibrary

Draws the screens. You write small functions called components — a participant row, a status pill, a form field — that each say "given this data, here is what I look like". React works out what changed and updates only that part of the page. It never reloads, because it was never loading pages in the first place; it is one page that redraws itself.

TypeScriptLanguage

JavaScript with the types written down. You declare that a participant has a full_name that is text and a room that is text, and the editor then catches a typo like fullName before the code ever runs. In a decoupled system this is what stops the two halves quietly drifting apart: src/api/types.ts is the written-down contract of what the back end sends.

ViteBuild tool

Browsers cannot read TypeScript or React directly, so something has to translate it into plain JavaScript. Vite does that — instantly while you are developing (save a file, the screen updates without losing your place) and once at the end to produce the files that ship.

React RouterLibrary

Decides which screen matches which address. /participants/4 shows Daniel's page. It changes the address bar and the back button works normally, but no page is ever fetched — it just draws a different component.

TanStack QueryLibrary

Handles asking the back end for data, and is doing more work than it sounds. It remembers answers so revisiting a screen is instant, knows when a cached answer is stale, retries a failed request, and gives every screen a plain loading / error / here-is-your-data state to render. Without it, every screen would hand-roll the same fiddly logic slightly differently.

Native CSSStyling

No Tailwind, no Sass. Plain modern CSS organised in numbered layers (ITCSS) with BEM naming — .c-participant__name reads as "the name part of the participant component". Deliberate: styling is the part most likely to be handed to someone else, and plain CSS is the one thing every web developer already knows.

The paperwork

WeasyPrintHTML → PDF

Takes an HTML page and prints it to a PDF, honouring page size, margins and repeating footers. This is why the generated record looks like the client's real form, boxed YES / NO and all — we describe the paper form in HTML and CSS and WeasyPrint prints it. It is also the one place Django still uses templates.

pypdfPDF stapler

Joins finished PDFs end to end. This is what builds a participant's record book out of their individual daily records.

The safety net

django-simple-historyAdd-on

Silently keeps a copy of every version of a record. If anyone ever asks "what did this say before it was changed", there is an answer.

django-otpAdd-on

Two-factor authentication — the six-digit code from an authenticator app. Intended for managers, who can see every participant in the service.

django-axesAdd-on

Locks an account after repeated failed logins, so nobody can sit there guessing passwords.

pytest & PlaywrightTesting

pytest runs the 52 automated checks that prove the important rules still hold — that a night shift is filed under the right day, that a worker cannot reach another house's participants. Playwright drives a real browser through the real screens, which is how the download bug and the "every participant says Not started" bug were both caught.

What it costs the phone The whole front end is about 107 KB compressed — 98 KB of JavaScript and 9 KB of CSS — downloaded once and then cached. Fonts add 134 KB, also once. That is a single modest photo, for the entire application.

04How the back end is organised

Django splits every feature into jobs with names. Learn these and the Python side opens up.

The wordPlain meaningIn this project
Model The shape of a thing, and its rules CareRecord says a record has a participant, a date, a shift, answers and a status. Django turns this into database tables for you.
View What happens when someone calls an address dashboard() works out who still owes a record this shift and returns that as data. In the old version it returned a page; now it returns JSON.
Serializer The translator between a database row and JSON ParticipantListSerializer decides that a participant sent over the wire has these eleven fields and not, for example, their emergency contacts.
URL routing The address book apps/api/urls.py is the entire public surface of the system on one screen — every address a client can call.

Two more words you will see constantly:

ORMObject-Relational Mapper

Lets you query the database in Python instead of SQL. Participant.objects.filter(home=acacia) means "every participant in Acacia House". Django writes the SQL. It also means nobody can inject malicious SQL through a form field — a whole class of attack simply does not apply.

MigrationDatabase change file

When you change a model — say you add a room number to Participant — Django writes a small file describing that change. Running it updates the database. Because these files live in the repository, every copy of the app can be brought to the same shape, in the same order, safely. It is version control for the database.

Apps: the filing system

Django encourages splitting a project into apps — self-contained folders, one per area of the business. Not separate programs; just tidy drawers.

AppOwns
apiEvery address, every serializer, sign-in, and the spreadsheet exports. The only app that touches HTTP.
peopleHomes, participants, staff and who may see whom
recordsThe care record itself, the form engine, shift arithmetic, filtering
noticesManager announcements and who has read them
pdfgenTurning records into PDFs and stapling books
Worth noticing api is thin on purpose. It knows how to receive a request and shape a reply, and nothing else. The actual thinking — which day a night shift belongs to, whether an answer is valid, who is allowed to see a participant — lives in people and records, where a future mobile API, a scheduled job or a management command can all reuse it.

05How the front end is organised

Four ideas, and you can read any screen in the project.

ComponentA piece of screen

A function that returns what something looks like. StatusPill takes a state and returns the little green "Complete" badge. ParticipantRow takes a participant and returns their row. Components are used wherever they are needed and only exist once, so the badge on the dashboard and the badge on the participants list can never look different.

ScreenA whole page

One file per thing you can navigate to — Dashboard.tsx, Participants.tsx, RecordForm.tsx. A screen asks for its data, then arranges components. There are ten.

StateWhat the screen currently knows

Which filters are set, what has been typed, whether the menu is open. When state changes React redraws whatever depended on it — you never write "now update that bit of the page", you just change the value.

QueryA request for server data

A named request handled by TanStack Query: ["participants"], ["record", 12]. Naming them is what lets one screen say "the dashboard numbers just changed, throw away what you cached" after a submit, so the next screen shows the truth instead of a stale copy.

Everything the front end knows about the back end goes through one small file, src/api/client.ts. It attaches the sign-in cookie, adds the security token described in section 09, and turns an error reply into a proper error a screen can display. No screen ever calls the network directly.

The rule that keeps this honest Business rules are never re-implemented in React. The form's "show this question only if they answered No twice" logic mirrors the schema the server sent, and the server validates it all again on submit regardless. The front end is allowed to be convenient. It is never allowed to be the authority.

06What happens when you tap something

Follow one tap all the way through. A worker taps Participants in the menu.

"But what if the JSON is huge?" Long lists are paged: the records screen asks for 25 at a time and the reply says how many exist in total, which is what draws "Page 1 of 3". Filtering happens on the server too — asking for "physio: yes" fetches only matching records, rather than downloading everything and hiding some.

What replaced the old page reloads

The first version used a small library called HTMX to avoid full page reloads. That whole idea is now gone, because there are no pages to reload — the browser loads the application once and then only ever exchanges data. Three practical consequences worth knowing:

Better
The screen keeps its place

Scroll position, half-typed answers, an open menu — none of it is thrown away when you navigate, because nothing is rebuilt.

Better
Going back is free

Returning to a screen you have already seen costs nothing at all. The data is already in memory.

Watch
Cached data can go stale

The one genuinely new failure mode. Submit a record and the dashboard would happily keep showing its old numbers unless the code explicitly says "that is out of date now". It bit us once in testing; there is now a named cache entry per screen and a submit clears the ones it affects.

07The four decisions everything rests on

Most of this codebase is ordinary. Four choices are not, and they are the reason it will be cheap rather than expensive to live with. All four survived the move to React unchanged, which is itself a decent sign they were the right ones. If you remember nothing else, remember these.

One — forms are data, not code

The obvious way to build a form is to write it: a model with a field per question, a screen with an input per question, a PDF layout to match. Do that and every new form the client asks for — Bowel Chart, Food Chart, Bruise Chart, Incident Report — is a fortnight of work and a deployment.

Instead, each form is a JSON schema: a plain text file listing the questions, their types, and the rules between them. The back end serves that file over the API, and the front end draws whatever it describes.

The rule that matters Every record stores which version of the schema it was filled under. Change the form in 2027 and a record signed in 2026 still renders under the 2026 rules. Without this, editing a form would silently rewrite history — which in a clinical system is a serious problem, not an inconvenience.

Two — answers are stored two ways at once

If answers are one flexible blob, adding a form is easy but reporting is agony. If every answer is its own database column, reporting is fast but every new form needs a database change. We do both.

One filter, two consumers The records screen and the spreadsheet export call the same filtering code. That is deliberate, and there is a test for it: a manager who filters the screen and then hits Excel must get exactly the rows they were looking at, not a differently-filtered set.

Three — a submitted record can never be edited

Once a worker submits, the record locks. Nobody edits it, ever — not the worker, not the manager, not an administrator. A correction is added as a separate amendment carrying who wrote it, when, and why, and it prints on the PDF underneath the original.

Alongside that, an audit log records not just changes but reads and downloads too. For health data, who looked at something matters as much as who altered it.

Why it had to be built in from day one This is how clinical records work everywhere, and an NDIS auditor will ask. It is also close to impossible to retrofit — once a system has let people edit records for a year, there is no honest history to reconstruct.

Four — a PDF is made once and never re-made

The instinct is to generate the PDF fresh whenever someone asks for it. That is wrong here. If the print layout changes in 2027, a record signed in 2026 would come out looking different from the one that was signed — the document would no longer be evidence of anything.

So the PDF is rendered once, at the moment of submission, and stored as a file. The record book is those stored files stapled together. History cannot shift.

Also true of dates A night shift starting 10pm Tuesday and ending 6am Wednesday belongs to Tuesday — the way it does in the paper book. The system stores the date the shift started separately from the moment it was submitted, and prints both. There is a test dedicated to this rule because getting it wrong would misfile records every single night.

08What happens when a worker taps Submit

This is the most important sequence in the system. It is also the place where decoupling changes the most, so it is worth reading closely.

  1. The answers are read and cleaned

    Anything the form was hiding at the time — the "if neither, why?" box when they actually did shower — is discarded, so a stale value typed earlier can never end up in the record. The server does this itself; it does not trust the front end to have done it.

  2. They are checked against the schema

    Fluids is required every shift. If it is blank the reply is a 400 naming that exact field, React puts the error under that question, and nothing is saved.

  3. The record locks

    Status becomes submitted, and who submitted it and exactly when are stamped on. A later attempt to write to it is refused with a 409 — "this is already settled".

  4. The reportable columns update

    Shower, physio, bowel and the rest are copied out of the answers so the manager's filters work.

  5. The PDF is rendered and stored

    Once. A fingerprint of the file is saved alongside it, so tampering would be detectable.

  6. An audit entry is written

    Who submitted what, and when.

  7. The finished record is sent back

    The reply is the whole saved record, so the app can show the locked version immediately without asking again. This is also where it must throw away its cached dashboard numbers — see the warning below.

A real bug this caused, worth understanding During testing, submitting a record correctly saved and locked it — the database proved it — but the screen still showed the old draft. The app was displaying its cached copy from before the submit. The fix is one line: on a successful submit, replace the cached record with the one the server just returned and mark the dashboard's numbers as stale. This is the characteristic bug of a decoupled front end, and it is the one to look for first when something "does not update".
Known limit, worth fixing before scale That 170 ms PDF render currently happens while the worker waits. Fine for three homes. At fifty it should move to a background queue so the submit returns instantly and the PDF is made a second later. The tool for it is already in the project's dependencies, just not switched on.

09Signing in, and why it is a cookie

When you decouple, you have to decide how the front end proves who it is on every single request. There are two common answers, and the choice has real security consequences. This one deserves the detail.

How a sign-in actually goes

  1. The app asks for a CSRF token

    A one-off value the server hands out, explained below.

  2. The username and password are posted to /api/auth/login/

    Over HTTPS. Passwords are stored hashed with Argon2, the current recommended algorithm — the server never holds the real password and could not tell you what it is.

  3. The server sets a session cookie

    Marked httpOnly (no script may read it), Secure (never sent over plain HTTP) and SameSite (not sent when another website triggers the request).

  4. Every later request carries it automatically

    The app does not manage this at all. The browser does it.

  5. The server decides what you may see

    Not the app. A support worker asking for another house's participant gets a 404, and a worker asking for the records screen gets a 403, regardless of what the menu happens to be showing them.

CSRF, in one sentence Because the browser attaches the cookie to every request to our domain, a malicious page could otherwise make your browser submit something on your behalf — so the server also demands a token that only our own app can read, which a page on another domain cannot obtain.
And the phone app later? A native app has no cookie jar and no shared origin, so it will use a token — but stored in the phone's Keychain or Keystore, the operating system's protected vault, which is a genuinely different proposition from browser storage. Django REST Framework can hand out both kinds of credential at once, so adding this changes nothing about how the website signs in.

Two guards, not one

The hiding of manager-only screens happens twice, on purpose:

  • The front end hides Records, Properties and Care workers from a support worker's menu, and sends them back to their own dashboard if they type the address. This is courtesy — it makes the app make sense.
  • The back end refuses those addresses outright. This is security — and it is the only one that counts, because anyone can edit what runs in their own browser.

Never rely on the first. Always implement the second. In this codebase the second one has tests; the first one does not need them.

10The folder map

Where to look when you want to change something. The top half is Python, the bottom half is TypeScript, and the two only meet at /api/.

config/ settings; splits into local and production apps/ api/ the entire HTTP surface urls.py every address, on one screen views.py what each address does serializers.py database rows → JSON, and back auth.py sign in, sign out, CSRF exports.py CSV, Excel, bulk PDF people/ homes, participants, staff models.py the shape of a Participant, a Home, a StaffProfile middleware.py remembers which house you are working in records/ the heart of the system models.py CareRecord, amendments, the audit log schema.py reads the form definitions, validates answers services.py shift arithmetic — which day does a night shift belong to filters.py the reportable-field filters, shared with exports pdfgen/ rendering PDFs and stapling books notices/ announcements forms/schemas/ the form definitions — add a form here templates/pdf/ the print layouts, one per form version tests/ the 52 checks frontend/ src/api/ client.ts the only file that talks to the network types.ts the written-down shape of every API reply src/screens/ one file per screen src/components/ the app frame and the shared pieces src/styles/ the styling, in numbered layers public/ logo, icons, fonts App.tsx which address shows which screen

The CSS uses ITCSS — the same layered approach as your existing cutups, just in modern CSS instead of LESS. Settings first (colours, type, spacing), then base elements, then layout objects, then components, then utilities. Anything later can override anything earlier, deliberately.

Running it Two processes in development: manage.py runserver 127.0.0.1:8811 for the API, and npm run dev for the app. You open port 5173 — Vite passes anything starting with /api through to Django, which mirrors what Caddy does in production so the cookie behaves identically. Opening Django's own port shows a 404, because it has no pages. That is correct.

11Where it goes from here

Not built yet

  • SharePoint sync. The client's headline ask. A background job pushes each participant's book to SharePoint via Microsoft's API, regenerating and replacing the file rather than appending to it. Deliberately last, because it sits on top of a working system and a SharePoint outage must never be able to block a worker's submission.
  • The Seizure Observation Chart as the second form — the test of whether the schema approach really pays.
  • Amendment screens. The model and the PDF rendering exist; the screen to write one does not.
  • Create and edit screens for participants and staff. The lists exist; adding is still done through Django's built-in admin.
  • PDF preview in the browser before saving. The download works; previewing does not exist yet.
  • Offline submission. Drafts already survive on the phone, but sending needs a connection.

Three things to fix before it gets big

WhatMeasured nowWhy it matters later
PDF made while the worker waits 170 ms Move it to a background queue so submitting returns instantly
Record book rebuilt from scratch 14 ms / page Three years of records would take roughly 30 seconds. It needs to build up rather than start over.
Dashboard queries each home separately 36 queries / 3 homes At fifty homes that becomes hundreds. One grouped query fixes it.

None of these touch the architecture. The data model, the form engine, the audit trail and the API surface all hold up.

If it becomes a real mobile app

This is now a straightforward piece of work rather than a rewrite, which was the entire point of decoupling.

The app talks to the same API this website already uses, with the same rules enforced the same way. It downloads the form schema and draws the form natively, so new forms still do not need an App Store release. What is actually needed is a token credential stored in the phone's secure vault, the screens rebuilt in the native toolkit, and a decision about offline behaviour. Weeks, not months, and nothing on the server has to change shape.

It is still worth asking whether the app is needed. The portal already installs to a phone's home screen and runs fullscreen. Native earns its place when you need the camera, fingerprint login, push notifications or true background sync — so decide on those, not on the idea of an app.
