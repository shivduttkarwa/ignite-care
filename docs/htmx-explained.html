A primer · companion to the architecture notes

HTMX, plainly

One idea, four attributes, five examples. If you can write HTML, you already know most of this.

Read this as background, not as a description of the portal The Ignite portal no longer uses HTMX. It was decoupled into a React front end and a JSON API, so there are no server-rendered pages left to swap. This primer is kept because the idea is worth knowing and it is the right tool for plenty of other jobs — but for how the portal actually works today, see the architecture notes.

01The one idea

In plain HTML, only two things can talk to the server: a link and a form. And both do the same blunt thing with the answer — throw away the entire page and replace it.

That is the whole limitation. Not that HTML is weak, but that it is restricted: only two elements may ask, only one thing may happen to the reply.

HTMX removes both restrictions. That is genuinely all it does.

QuestionPlain HTMLWith HTMX
What can ask the server?Links and forms onlyAny element — a button, a div, a table row
When does it ask?On click, or on submitAny event — typing, hovering, every 5 seconds
Where does the answer go?The whole page, alwaysAny element you name
How does it go in?Replaces everythingReplace, append, prepend, or delete
The part that surprises everyone The server sends back HTML, not JSON. There is no data to convert, no template to render in the browser, no state to keep in sync. The server sends a finished chunk of page and HTMX puts it where you said. That single decision is why there is no build step and no second codebase.

02Four questions, four attributes

Every HTMX attribute answers one of four questions. Learn these and you have learned the library — the rest is detail.

1
What sets it off? hx-trigger="click"

A click, a keystroke, the mouse entering, a timer. If you leave it out, HTMX guesses sensibly: a button uses click, an input uses change.

2
Where does it go, and how? hx-get="/url"

Also hx-post, hx-put, hx-delete. Same verbs a form already has, now available on anything.

3
Where does the answer land? hx-target="#results"

Any CSS selector. Leave it out and the answer replaces the element that asked.

4
How does it land? hx-swap="innerHTML"

Fill it, replace it, add to the end, add to the start, or delete it. innerHTML is the default and is usually what you want.

Read any HTMX attribute as a sentence and it makes sense: "when this is clicked, GET this URL, and put the answer inside that element."

03Five examples, smallest first

Example 1 A button that loads something
What you write 
<button hx-get="/notices"
        hx-target="#panel">
  Show notices
</button>

<div id="panel"></div>
What the server sends back 
<!-- just HTML. no JSON. -->
<p>Grocery delivery moved</p>
<p>New sensor mat installed</p>
What the user sees
Show notices
Grocery delivery moved
New sensor mat installed

Read it as a sentence: when this button is clicked, GET /notices, and put the answer inside #panel. No JavaScript was written. The page never reloaded.

Example 2 Search that updates as you type
What you write 
<input type="search" name="q"
       hx-get="/participants/search"
       hx-trigger="keyup changed delay:300ms"
       hx-target="#results">

<div id="results"></div>
What the user sees

The input's own name="q" is sent automatically. You never touch a query string.

The clever bit is delay:300ms. It waits until typing pauses before asking, so a five-letter name is one request, not five. Doing that by hand in JavaScript is called debouncing and takes about fifteen lines. Here it is one word.

What you write 
<tr>
  <td>Daniel Reeves</td>
  <td>
    <button hx-delete="/record/12"
            hx-target="closest tr"
            hx-swap="outerHTML"
            hx-confirm="Delete this?">

</tr>

Three things worth noticing. closest tr means "the table row this button sits in" — no ids needed. hx-confirm pops a confirmation with no JavaScript. And the server replies with nothing at all, which combined with outerHTML means the row simply vanishes.

Example 4 A number that keeps itself up to date
What you write 
<span hx-get="/outstanding-count"
      hx-trigger="every 30s">
  2
</span>

No target given, so the answer replaces what is inside the span itself.

What the user sees
Outstanding 2
refreshes itself every 30 seconds

Polling in one attribute. A manager leaves the dashboard open all shift and the outstanding count keeps itself current, without a websocket, a framework, or a line of JavaScript.

Example 5 The whole site, in one attribute
What you write 
<body hx-boost="true">

  <!-- every link and form below -->
  <!-- is now handled by htmx     -->

  <a href="/participants/">Participants</a>
  <a href="/records/">Records</a>

</body>
What changes

Those links look completely ordinary, and they still work if JavaScript fails. But when it is running, clicking one no longer reloads the page — HTMX fetches it and swaps in the new body.

The stylesheet stays loaded. The fonts stay loaded. Nothing flashes white.

This is the one being used on the care portal. Measured: 67–106 ms per page, zero full reloads.

This is the same idea as examples 1 to 4, just applied automatically to every link instead of one element at a time. Nothing new to learn.

04How this differs from React

Both give you a page that updates without reloading. They disagree about where the HTML gets made, and everything else follows from that.

A fair summary React is the right answer when the browser genuinely needs to own some state — a drag-and-drop planner, a spreadsheet, a drawing tool, anything that must work offline. HTMX is the right answer when the server already knows everything and the browser just needs to show it. Forms and lists — most business software, in other words — sit firmly in the second group.

05When not to use it

Every honest tool description includes this section.

  • When it must work offline. Every HTMX interaction is a request. No connection, no update. A client-side app can keep working from data it already holds.
  • When the interaction must be instant and continuous. Dragging, resizing, drawing, a canvas. A round trip per frame is obviously wrong.
  • When one change updates six places at once. Doable with HTMX, but this is where a framework's state management genuinely earns its keep.
  • When there is already a mobile app sharing an API. If a JSON API must exist anyway, having the web app use it too is reasonable.
Three things that catch people out

Analytics stops recording. Google Analytics fires on page load, and boosted navigation has none — you must fire it yourself on htmx:afterSettle.

Third-party widgets stop initialising. Sliders and embeds scan the page once on load. Re-run them on htmx:load.

Downloads must opt out. Add hx-boost="false" to any link returning a file, or HTMX will helpfully swap a spreadsheet's raw binary into your page. This genuinely happened on the care portal.

06The whole cheat sheet

This is very nearly all of HTMX. There is more, but you can build a great deal with only this.

AttributeWhat it does
hx-get hx-postAsk the server, using that method. Also hx-put, hx-patch, hx-delete.
hx-triggerWhat sets it off. click, keyup, every 30s, load, revealed.
hx-targetWhere the answer lands. Any selector, or closest tr, next div.
hx-swapHow it lands. innerHTML, outerHTML, beforeend, delete.
hx-boostApply all of the above automatically to every link and form.
hx-confirmAsk "are you sure?" first.
hx-indicatorShow a spinner while waiting.
hx-selectTake only part of the response and ignore the rest.
hx-preserveKeep this element untouched across a swap.
hx-valsSend extra values along with the request.

Getting it onto a page

<script src="/static/js/htmx.min.js" defer></script>

One file, about 14 KB. No installation, no build, no configuration. Drop it in a Django template, a Wagtail base template, a WordPress header, or a plain HTML file, and every attribute above starts working.
